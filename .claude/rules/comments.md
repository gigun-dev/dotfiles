# コメント方針(このリポジトリの基本ルール)

**コメントをコードと同量レベルでベッタベタに書く。** AI が主に読み書きするコードでは
「自己説明的であるべき」慣習は当てはまらない(乖離は AI が検知できる/情報量のメリットが勝る)。
一次資料: https://x.com/yuki_arano/status/2067462860771623245

1. **「意図」を残す** — なぜこの値/この実装か、をコードのすぐ隣に。マジックナンバーには理由必須。
2. **経緯も残す** — `// 2026-05-12 クラッシュ修正: ○○が原因。△△は試したがダメだった` 歓迎。
   ボツ案は次に同じ道を通らないための財産。
3. **コンテキストはコードの近くに** — 別ドキュメントに切り出さない。
4. **分量目安**: 関数はコメント:コード ≒ 半々。既存コメントを消すのは「事実として誤りになった」
   ときだけ。冗長という理由では消さない。

## このリポジトリで特に効く場所

- **flake.nix の `follows` と overlay の判断** — 最も改悪されやすい。llm-agents / cclens は
  あえて `nixpkgs.follows` を付けていない (統一すると我々の nixpkgs で再ビルドされ、上流の
  専用キャッシュに当たらず Rust フルビルドになる)。「規約どおり統一した方が綺麗」に見えるので、
  **なぜ外しているかを必ず隣に書く**。overlay での `overrideAttrs` も同様にハッシュを変えて
  キャッシュを壊すため、理由と影響範囲を残す
- **`.zshrc` の compinit まわり** — WSL / Nix 固有の落とし穴が集中している (`compinit -u` の理由、
  `.zcompdump` を source するだけでは `_comps` が空になること、Nix の zsh が Completion
  サブディレクトリを自動 fpath 追加しないこと)。どれも消すと静かに補完が全滅する
- **`nix/modules/nixos/mini-vm.nix` の boot / fileSystems** — nixos-lima が配布するイメージの
  レイアウトに合わせた固定値。整理したくなるが変えるとブートしない
- **冪等性のためのガード** — `apple-container.nix` の存在チェックのように、「なぜ無条件に実行
  できないか」(`kernel set --recommended` は再実行すると "File exists" で落ちる) を書く。
  理由が無いと次に読む人が「冗長」と判断して外す
- **プラットフォーム分岐の理由** — `packages.nix` では codex と agy が同じ条件式を共有しているが
  理由は別 (codex は Intel での Rust フルビルド回避、agy は llm-agents が x86_64-darwin 未収録)。
  条件が同じでも由来が違うものは、まとめる前に理由を確認する
- **順序に意味がある手順** — iTerm2 の bootstrap (起動前に最初の switch を終える) のように、
  守らないと静かに壊れるものは手順の理由まで書く
