# コメント方針(このリポジトリの基本ルール)

**必要十分に書く。多いほど良いではない。** 冒頭に「何を守るか・何の事故を止めるか」、
行には「その行の理由」だけ。

## 残すもの

1. **意図** — なぜこの値/この実装か。マジックナンバーには理由必須。
2. **障害の記録** — `2026-05-12 修正: ○○が原因。△△は試したがダメだった`。
   日付・原因・試して駄目だったものは、次に同じ道を通らないための財産。
3. **ボツ案** — ただし**再提案されそうなものだけ**。「綺麗に見えるが壊れる」類型が本命。
4. **非自明な制約** — 消すと静かに壊れるもの(下記「特に効く場所」)。

## 書かないもの

- **コードを読めば分かること** — `# gc を有効にする` の類。
- **同じ内容の言い換え** — 1 つの事実は 1 箇所に。ファイル内で同じ説明が 2 回出てきたら、
  片方は消して参照に替える。
- **一般論** — その技術の教科書的説明。ここに固有でないなら要らない。
- **網羅的なボツ案の列挙** — 誰も再提案しない案は書かない。

## 書き方

- **訂正は置き換える。** 旧文を残すのは 1 行まで(`以前は X としていたが誤り`)。
  訂正の経緯を積層すると、読む側は毎回全部通る。
- **コンテキストはコードの近くに。** 別ドキュメントへ切り出さない。
- **消してよいのは**「事実として誤りになった」ときに加え、**重複・言い換え**のとき。
  障害の記録と非自明な制約は、冗長に見えても消さない。

## このリポジトリで特に効く場所

- **flake.nix の `follows` と overlay の判断** — 最も改悪されやすい。llm-agents / cclens は
  あえて `nixpkgs.follows` を付けていない (統一すると我々の nixpkgs で再ビルドされ、上流の
  専用キャッシュに当たらず Rust フルビルドになる)。「規約どおり統一した方が綺麗」に見えるので、
  **なぜ外しているかを必ず隣に書く**。overlay での `overrideAttrs` も同様
- **`.zshrc` の compinit まわり** — WSL / Nix 固有の落とし穴が集中している (`compinit -u` の理由、
  `.zcompdump` を source するだけでは `_comps` が空になること、Nix の zsh が Completion
  サブディレクトリを自動 fpath 追加しないこと)。どれも消すと静かに補完が全滅する
- **`nix/modules/nixos/mini-vm.nix` の boot / fileSystems** — nixos-lima のイメージに
  合わせた固定値。整理したくなるが変えるとブートしない
- **冪等性のためのガード** — `apple-container.nix` の存在チェックのように「なぜ無条件に実行
  できないか」(`kernel set --recommended` は再実行すると "File exists" で落ちる)。
  理由が無いと次に読む人が「冗長」と判断して外す
- **プラットフォーム分岐の理由** — `packages.nix` の codex と agy は同じ条件式だが理由は別
  (codex は Intel での Rust フルビルド回避、agy は llm-agents が x86_64-darwin 未収録)。
  条件が同じでも由来が違うものは、まとめる前に理由を確認する
- **順序に意味がある手順** — iTerm2 の bootstrap (起動前に最初の switch を終える) のように、
  守らないと静かに壊れるものは手順の理由まで書く
- **秘密の所有権とパス** — `secrets/` と agenix。所有者を間違えると「復号は成功するのに
  読めず、サービスは起動して黙る」形で壊れる (mini-vm.nix の gatekeeper 秘密で実際に発生)
